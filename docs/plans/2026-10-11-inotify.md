# inotify, for `FileSystemWatcher` on the Linux CoreLib

## Goal

Kestrel and `HttpClient` run as two PawPrint processes on one machine
(#1846, `TestAspNetTwoProcess`). That test has to set
`DOTNET_USE_POLLING_FILE_WATCHER=1`, because ASP.NET's configuration
reload (`AddJsonFile("appsettings.json", reloadOnChange: true)`, through
`PhysicalFileProvider`) starts a `FileSystemWatcher`, and on the Linux CoreLib
that is inotify, which neither `WoofWare.PosixKernel` nor PawPrint models. The
goal is a general inotify in the kernel library, with no CoreCLR concept in it,
the three shim entry points in PawPrint, and that environment variable gone
from the test.

This document is the measurement and design phase. Nothing here changes the
kernel.

## 1. What exists

**In `WoofWare.PosixKernel`, on main (`7d700bb6`).**

- An open file description's kind is `OpenFileTarget`: `File`, `Directory`,
  `Epoll of EpollState`, `Kqueue of KqueueState`, `Socket`, `Pipe`,
  `CharacterDevice`. An epoll instance is the model closest to what an inotify
  instance is: a kernel object that *is* its open file description, created by
  one syscall, carrying its own table and its own queue, destroyed with its last
  reference, and payload-free as a `flock` object (`OpenFileObject.AnonymousInode`,
  because every anon-inode file in a process shares one inode).
- Descriptions live on the machine (`UnixMachineState.OpenFiles`), so a
  change made in one process's view is visible to every other process's parks
  (`2026-10-07-multi-process-machine.md`, decision 2). `SimulatedMachine.wakes`
  asks each sleeping task's `WakeCondition` of its own view, against the shared
  `OpenFiles`.
- A blocking read parks (`ParkedSyscall.PipeRead`, `ConnectionRead`), with a
  `WakePrimitive` per thing it waits for, and finishes through
  `UnixReadWrite.finishRead`. A park holds the descriptions it names
  (`ParkedSyscall.descriptions`), so a description closed under a sleeping
  Linux read lives until the read returns.
- Linux readiness is one function over the target kind
  (`LinuxReadiness.ofDescription`), read by `poll` and by epoll's re-poll.
  `epoll_ctl` admits sockets and pipes and answers `EPERM` for a regular file.
- Every filesystem mutation is a function in `VirtualFileSystem`
  (`createFile`, `createDirectory`, `createSymlink`, `hardLink`, `unbind`,
  `rename`, `writeFile`, `truncateFile`, `setPermissions`, `setOwner`,
  `setTimes`, `cloneFile`, `forget`), and about twenty-five call sites across
  `UnixNamespace`, `UnixPathResolution`, `UnixReadWrite`, `UnixDescriptor` and
  `ObjectLifetime` store the result with `{ machine with FileSystem = ... }`.
  A directory's entries are `Map<DirectoryEntryName, InodeNumber>`: there is
  no dentry object, so nothing records *which name* a description was opened
  through.
- The path walk answers the final component as
  `ResolvedTarget.Entry (directory, name, existing)`, so every path syscall
  has the parent directory and the name in hand at the moment it acts.
- `/dev` is a devtmpfs the kernel mounts at boot. Listing it is refused
  (`ReadDirectoryRefusal.DeviceFileSystem`), because a real one holds hundreds
  of nodes and the model holds two.

**In PawPrint.** `SystemNative_Read`, `SystemNative_Poll`, `SystemNative_LStat`,
`SystemNative_OpenDir`/`ReadDir`, `SystemNative_FStat`, `SystemNative_LSeek`
and `SystemNative_Close` exist. There is no handler for
`SystemNative_INotifyInit`, `SystemNative_INotifyAddWatch` or
`SystemNative_INotifyRemoveWatch`; a call reaches `NativeCall.failUnimplemented`,
which names the import. `2026-08-23-socket-poll.md` noted in passing that
`FileSystemWatcher` polls an inotify descriptor, a kind PawPrint does not have.

**In the test.** `TestAspNetTwoProcess` runs both guests with
`DOTNET_USE_POLLING_FILE_WATCHER=1` and the current directory `/`, and the real
runtime's two processes in one scratch directory holding a subdirectory per
guest (`RealRuntime.executeConcurrently`).

## 2. What the managed code does with the descriptor

Read from the pinned runtime source (`4271d88`): `FileSystemWatcher.Linux.cs`,
`Common/src/Interop/Linux/System.Native/Interop.INotify.cs`,
`Microsoft.Extensions.FileProviders.Physical/PhysicalFilesWatcher.cs`, and
`WebApplicationBuilder.cs` of aspnetcore `release/10.0`. These are not in the
devshell's sparse checkout; the plan directory does not copy them.

**How the Kestrel path reaches it.** `WebApplication.CreateSlimBuilder` sets the
content root to the current directory and adds `appsettings.json` and
`appsettings.{env}.json` with `reloadOnChange: true`
(`ApplyDefaultAppConfigurationSlim`). The host's `PhysicalFileProvider` for
the content root makes one `FileSystemWatcher(root)` with
`IncludeSubdirectories = true` and the default `NotifyFilters`
(`LastWrite | FileName | DirectoryName`). Loading each JSON source calls
`FileProvider.Watch(path)`, and the first token enables the watcher. Neither
file exists; the tokens exist regardless, so the watcher runs for the life of
the host. Only the server has a host; the client is a bare console program and
starts no watcher.

**What enabling does.** `StartRaisingEvents`:

1. `SystemNative_INotifyInit()`: `inotify_init1(IN_CLOEXEC)`. `EMFILE` and
   `ENFILE` become `IOException`s whose message reads
   `/proc/sys/fs/inotify/max_user_instances`.
2. `inotify_add_watch(fd, root, mask)` with the mask
   `IN_CREATE | IN_DELETE | IN_MODIFY | IN_ATTRIB | IN_MOVED_FROM | IN_MOVED_TO | IN_ONLYDIR | IN_EXCL_UNLINK`
   (`TranslateFilters`; `IN_ATTRIB` and `IN_MODIFY` come from `LastWrite`,
   `IN_MOVED_*` from `FileName | DirectoryName`; `IN_ACCESS` only under
   `LastAccess`, which nothing here sets; `IN_DELETE_SELF` is deliberately not
   asked for). Then, because `IncludeSubdirectories`, `Directory.EnumerateDirectories(root)`
   and for each subdirectory `LStat` (skipping symlinks) and
   `inotify_add_watch` with `IN_DONT_FOLLOW` added, recursively. `ENOENT` and
   `ENOTDIR` on a child are ignored; any other failure raises the `Error`
   event; `ENOSPC` reads `max_user_watches`. A watch descriptor already in its
   map is a rename.
3. A dedicated background thread, `.NET File Watcher`, loops on a blocking
   `SystemNative_Read(handle, buf, 8192)` (`_internalBufferSize`, through
   `Interop.CheckIo`; an `ArgumentException` from a buffer too small is
   asserted against and treated as zero bytes). No epoll. `SystemNative_Poll`
   is called in one place: after an `IN_MOVED_FROM` that ends the buffer, with
   `POLLIN` and a 2 ms timeout, to decide whether an `IN_MOVED_TO` is coming.
4. Each record: `wd` (int32), `mask`, `cookie`, `len` (uint32s), then `len`
   bytes of name of which the NUL and anything after it are dropped. An
   unknown `wd` is ignored. `IN_Q_OVERFLOW` raises the overflow event and
   restarts the whole instance. `IN_ISDIR | IN_IGNORED` means the subject is
   a directory. `IN_MOVED_FROM` is held until the next record; an adjacent
   `IN_MOVED_TO` with the same cookie is a rename, anything else makes it a
   deletion. `IN_IGNORED` removes the directory from the map without calling
   `inotify_rm_watch`. `IN_CREATE | IN_ISDIR` or `IN_MOVED_TO | IN_ISDIR` adds
   a watch for the new subdirectory.
5. Stopping (`EnableRaisingEvents = false`, or dispose) cancels a token whose
   callback calls `inotify_rm_watch` on every watch descriptor it holds. The
   comment says this makes the blocking read return 0 bytes; in fact it makes
   the read return `IN_IGNORED` records (section B of the probe), after which
   the loop sees the cancellation and exits, and only then disposes the handle.
   The thread never relies on `close` to end its read, and `IN_IGNORED` is
   what ends it; a kernel that did not queue `IN_IGNORED` on `rm_watch` would
   leave that thread asleep for ever. `INotifyRemoveWatch` treats `EINVAL` as
   success (the watch went with its directory).

**What the Kestrel path makes the kernel do**, in order: `inotify_init1`;
`inotify_add_watch(cwd)` with the mask above and no subdirectories to add
(under PawPrint `/app` would hold nothing else; see 4.9); a `read` that
parks; the server's `File.WriteAllText(handoff + ".tmp")` (`open(O_CREAT|O_TRUNC)`,
`write`, `close`) queues `IN_CREATE` and `IN_MODIFY` and wakes the reader;
`File.Move` queues `IN_MOVED_FROM` and `IN_MOVED_TO` in one syscall; the
client's `File.Exists` and `File.ReadAllText` queue nothing under that mask;
at `StopAsync` the provider disposes the watcher, `inotify_rm_watch` queues
`IN_IGNORED`, the reader thread exits and closes the descriptor. Every event
here is raised by the server in its own process, so the Kestrel path does
not exercise a cross-process wake; section 5 tests one anyway.

**Darwin.** The Darwin CoreLib's `FileSystemWatcher` is `FileSystemWatcher.OSX.cs`
over `Interop.EventStream` (`FSEventStreamCreate` and friends in CoreServices,
with a `CFRunLoop`), a different mechanism entirely. See 4.8.

## 3. Measured facts

**Probe.** `2026-10-11-inotify/inotify-probe.c`, output
`inotify-probe.linux-6.18.5-aarch64.txt`: Linux 6.18.5 aarch64 in Apple's
`container` VM (Debian trixie, glibc 2.41), as root, default sysctls. Run
three times, in two container boots; every line not marked `~boot` agreed
between runs. The probe's header lists its sections and what each line
reports; an event is rendered `wd=N mask=NAMES cookie=kN len=L name="..."`,
with cookies numbered in the order the probe first saw them.

Nothing here depends on the architecture: `struct inotify_event` is four
32-bit fields in both ABIs, and both modelled Linux architectures are
little-endian. Stage 3's host-equality test runs on CI's x86-64 and will say
so or not.

### 3.1 The descriptor (section I)

- Two inotify descriptors and an epoll descriptor report one `st_dev` and
  one `st_ino` (13 and 15 in one boot, 13 and 1025 in another), mode 0600,
  one link, size 0. With `LOCK_EX|LOCK_NB` held through the epoll descriptor,
  the same request through an inotify descriptor is `EAGAIN`, and once released,
  a second inotify descriptor's request is `EAGAIN` against the first's. So an
  inotify instance is `OpenFileObject.AnonymousInode`, with epoll.
- `lseek` answers 0 for `SEEK_SET`, `SEEK_CUR` and `SEEK_END` at offsets 0 and
  5 (`noop_llseek`, as epoll).
- `F_GETFL` is 0 after `IN_CLOEXEC` alone (access mode `O_RDONLY`, no
  `O_NONBLOCK`) and `04000` after `IN_CLOEXEC|IN_NONBLOCK`; `F_GETFD` is 1
  (`FD_CLOEXEC`). `write` of one byte answers `EBADF`: the read-only access
  mode's answer, not a kind-specific one.
- An empty instance: `poll(IN|OUT|PRI|RDHUP, 0)` is 0 with no bits,
  `FIONREAD` 0, non-blocking `read(64)` `EAGAIN`.

### 3.2 Watches (section W)

- Watch descriptors are 1, 2, ... per instance. Adding the same directory
  again, or through `./w/d1/.`, answers the existing descriptor and queues
  nothing. After `inotify_rm_watch` of 1, re-adding that directory answers 5
  (one past the highest ever allocated): descriptors are never reused.
- A file with `IN_ONLYDIR` is `ENOTDIR`; without it, a file is watched (wd 3).
  A missing path is `ENOENT`; a mask of 0 is `EINVAL`; a mask holding only
  `IN_ONLYDIR` succeeds (answering the existing wd). A descriptor that names
  nothing is `EBADF`; one that names a regular file is `EINVAL`.
- A symbolic link to a directory is followed without `IN_DONT_FOLLOW` (the
  directory's wd comes back) and watched as itself with it (a fresh wd);
  `IN_DONT_FOLLOW|IN_ONLYDIR` on a link is `ENOTDIR`.
- Re-adding replaces the mask (under `IN_MODIFY` alone a `chmod` queues
  nothing); `IN_MASK_ADD` unions it; `IN_MASK_CREATE` on an existing watch
  is `EEXIST`.
- `inotify_rm_watch` of a live wd is 0 and queues `IN_IGNORED` for it (len 0);
  of that wd again, of 999 and of -1, `EINVAL`.

### 3.3 Which events each operation raises (sections E and N)

Under `IN_ALL_EVENTS` on a directory, each operation on an entry queues, with
the entry's name:

| operation | records |
|---|---|
| `open(O_CREAT\|O_EXCL)` | `CREATE`, then `OPEN` |
| `write` of 5 bytes, `pwrite`, `ftruncate`, `truncate(path)` | `MODIFY` |
| `write` of 0 bytes | nothing |
| `close` of a descriptor written through | `CLOSE_WRITE` |
| `open(O_RDONLY)`, `read`, `close` | `OPEN`, `ACCESS`, `CLOSE_NOWRITE`; a read at end of file queues nothing |
| `open(O_WRONLY\|O_TRUNC)` of an existing file | `OPEN`, then `MODIFY` |
| `chmod`, `chown`, `utimensat` | `ATTRIB` |
| `chmod` of the watched directory itself | `ATTRIB\|ISDIR`, len 0 |
| `mkdir`, `rmdir` | `CREATE\|ISDIR`, `DELETE\|ISDIR` |
| a write inside an unwatched subdirectory | nothing |
| `symlink`, `link` | `CREATE` (no `ISDIR`) |
| `unlink` of one of two names, of a symlink, of a file | `DELETE` |
| `rename` within the directory | `MOVED_FROM` (old name), `MOVED_TO` (new name), one cookie |
| `rename` over an existing name | the same two, and **nothing for the displaced name** |
| `rename` in from an unwatched directory | `MOVED_TO` alone; out to one, `MOVED_FROM` alone |
| `rename` of a subdirectory | the pair with `ISDIR` |
| `rename` of a name onto itself | nothing |

Under the mask `FileSystemWatcher` uses (section N), the same operations
queue exactly the subset of those records whose bits are in the mask, and
nothing else: `OPEN`, `CLOSE_*` and `ACCESS` rows are empty, and
`open(O_CREAT)` queues `CREATE` alone.

### 3.4 A watch on a file (section F)

Two names of one inode give one wd. Events on it have len 0. `MOVE_SELF` on
rename of the watched name. Unlinking the *other* name queues `ATTRIB` (the
link count changed). Unlinking the last name while a descriptor is open queues
`ATTRIB` only; the `close` of that descriptor then queues `CLOSE_NOWRITE`,
`DELETE_SELF`, `IGNORED`, in that order, and `inotify_rm_watch` of the wd is
`EINVAL` afterwards. So the inode's own deletion events come when the inode is
*forgotten* (last name and last reference gone), not when its last name goes.

### 3.5 Watched things deleted and moved (section D)

- Renaming a watched subdirectory: the parent's `MOVED_FROM|ISDIR` and
  `MOVED_TO|ISDIR`, then the subdirectory's own `MOVE_SELF`. Its wd keeps
  working under the new name.
- `rmdir` of a watched subdirectory: **the subdirectory's `DELETE_SELF`, its
  `IGNORED`, and then the parent's `DELETE|ISDIR`**. The child's records come
  before the parent's.
- Moving a watched subdirectory out of the watched tree: `MOVED_FROM|ISDIR` at
  the parent and `MOVE_SELF` at the child; the child's wd goes on reporting
  events (a file created there queues `CREATE` and the rest).
- A file unlinked while open, under a parent watch: without `IN_EXCL_UNLINK`
  a later `write` through the open descriptor queues `MODIFY` with the *old*
  name; with `IN_EXCL_UNLINK` on the parent's watch, the write and the close
  queue nothing.

### 3.6 Hard links, and the name an event carries (section H)

A file with names `h/a`, `h/b` and `h/other/c`, with `h` and `h/other`
watched, opened through all three:

- a `write` through the descriptor opened as `a` queues `MODIFY "a"` at `h`;
  through `b`, `MODIFY "b"` at `h`; through `other/c`, `MODIFY "c"` at `other`.
  `fchmod` likewise names the descriptor's own name;
- after `rename("h/a", "h/renamed")`, a write through the first descriptor
  queues `MODIFY "renamed"`; after `rename("h/renamed", "h/other/moved")`,
  it queues `MODIFY "moved"` **at `other`'s watch**;
- after `unlink("h/b")`, a write through `b`'s descriptor still queues
  `MODIFY "b"` at `h` (no `IN_EXCL_UNLINK` on that watch).

So an event raised through a descriptor goes to the watch on the *parent of
the name the descriptor was opened through*, carrying that name as it is
now: the kernel's dentry, which `rename` moves (`d_move`) and `unlink` leaves
named.

### 3.7 Record layout (section L)

`sizeof(struct inotify_event)` is 16. `len` is the name's length plus the
NUL, rounded up to a multiple of 16: names of 1 to 15 bytes give 16, 16 to 31
give 32, 32 gives 48, 255 gives 256; the padding is all zero.

### 3.8 Coalescing (section C)

A record identical to the **last** one queued (wd, mask, cookie, name) is
dropped: three writes to one file queue one `MODIFY`; `chmod f`, `chmod f`
queue one `ATTRIB`. A different record between two identical ones keeps both
(`MODIFY`, `ATTRIB`, `MODIFY`; `ATTRIB f`, `ATTRIB g`, `ATTRIB f`), and so does
a read between them.

### 3.9 `read` (section R)

With one 32-byte record queued: `read` with count 0, 15, 16 or 31 is `EINVAL`;
32 returns it. With two 32-byte records, `read(48)` returns 32 (one record),
and the next `read(1024)` the other. Empty and non-blocking, counts 0 and 1024
are both `EAGAIN`. `read(NULL, 1024)` with a record queued is `EFAULT` **and
the record is gone**: the next read is `EAGAIN`.

### 3.10 Readiness (section P)

`poll(IN|OUT|PRI|RDHUP)` reports `0x1` with a record queued, and 0 after the
queue drains or when only `POLLOUT` is asked. (That request does not ask for
`RDNORM`; asked with every bit, both waiters report `0x41`, `IN|RDNORM`: 3.16.)
`epoll_ctl(ADD)` succeeds, `epoll_wait` reports `EPOLLIN` with the
registration's data, and a level-triggered registration reports again while
the queue stays non-empty.

### 3.11 Cookies and instances (sections K and A)

Two renames give two cookies differing by 1, both halves of each sharing one;
a second instance watching the same directory sees the same cookie. The first
cookie's value (7535, 7544, 7561) counts every rename since boot. Two
instances on one directory both get every event; a `dup` shares the instance
(a read through it drains the original), and closing the dup leaves the
instance working.

### 3.12 Queue limit and overflow (section O)

`/proc/sys/fs/inotify`: `max_user_instances` 128, `max_queued_events` 16384,
`max_user_watches` 8982 (derived from the VM's memory). 21,384 alternating
`chmod`s queue 524,304 bytes (`FIONREAD`): 16,384 records and then **one**
record `wd=-1 mask=IN_Q_OVERFLOW cookie=0 len=0` as the 16,385th, and nothing
after it. Once drained, the next operation's record arrives. A second fill gives
again 16,385 records with one overflow record. A watch added while the queue is
full gets a wd, its events are dropped like the rest, and after the drain they
arrive.

### 3.13 A thread blocked in `read` (section B)

A blocking read with no record queued does not return. An event returns it
with that record. `inotify_rm_watch` of the only watch returns it with the
16-byte `IN_IGNORED` record. A read on an instance with no watches does not
return in 150 ms; `close` of the descriptor by another thread does not return
it in 150 ms either (the read holds the file, as a pipe's does on Linux).
A signal with a handler ends it with `EINTR`; under `SA_RESTART` it goes on
sleeping and returns the next event.

### 3.14 Per-user limits (section S)

127 instances were created before `EMFILE`, and 8,981 watches before `ENOSPC`,
each one short of the sysctl: something else in the VM (its init process, at
uid 0) presumably holds one instance with one watch. The rule is a per-user
count against the sysctl; the exact accounting is for stage 3's host test to
state (3.15).

### 3.16 Measured for stage 3

From `inotify-instance-probe.c` and `inotify-descriptor-probe.c`, Linux 6.18.5
aarch64, as root and from uid 65534:

- **`inotify_init1`** accepts `IN_NONBLOCK` (04000) and `IN_CLOEXEC`
  (02000000) and nothing else (F).
- **`inotify_add_watch`'s order** (G): a mask naming a bit `<sys/inotify.h>`
  does not define, or no bit, is `EINVAL` ahead of `EBADF`; then `EBADF`; then
  `IN_MASK_ADD|IN_MASK_CREATE`, or a descriptor that is not an instance,
  `EINVAL`; then the path (`EFAULT` for NULL, `ENOENT` for ""); then `EACCES`
  without read permission on the inode (a 0711 or 0733 directory, a 0200
  file). The kernel-added bits (`IN_ISDIR`, `IN_IGNORED`, `IN_Q_OVERFLOW`) and
  every flag alone are accepted, and a mask of `IN_ISDIR` alone re-added over a
  watch leaves it asking for nothing (M).
- **Per-user limits** (U), from a uid holding nothing: 128 instances and 8982
  watches (the VM's sysctls exactly), counted across instances; re-adding an
  existing watch at the limit succeeds; and **an add refused `ENOSPC` spends
  its watch descriptor** (`idr_alloc_cyclic` runs before the count).
- **The queue** (Q): the limit is tested **before** the repeat check, so a
  repeat of the newest record at a full queue adds the `IN_Q_OVERFLOW`; after
  a read of two records from an overflowed queue a new record follows the
  overflow record; the repeat check **ignores the cookie** (two
  `IN_MOVED_FROM` of one name, different cookies, coalesce).
- **Edge-triggered epoll** (T) is woken by every record queued, a second one
  behind one already reported included, and not by a record that coalesces.
- **`read`** (X, and descriptor-probe S): `read(NULL, 0)` with a record is
  `EINVAL` and keeps it; a fault partway through loses every record taken; a
  sleeping read woken by a record larger than its count answers `EINVAL`; of
  two readers asleep when the description became non-blocking, one takes the
  record and the other answers `EAGAIN`.
- **Calls that are not inotify's own** (descriptor-probe D, N): `isatty`
  `ENOTTY`, `pread` and `pwrite` `ESPIPE`, `write` of nothing `EBADF`,
  `FIONREAD` to NULL `EFAULT`, `posix_fadvise` 0, `ftruncate` and `FICLONE`
  `EINVAL`, `getdents64` `ENOTDIR`, `recv` `ENOTSOCK`; `F_SETFL O_NONBLOCK`
  takes, and `F_GETFL` then reads 04000.
- **Readiness asked with every bit** (descriptor-probe P): `poll` and epoll
  report `0x41`, `IN|RDNORM`, with a record queued. 3.10's request did not ask
  for `RDNORM`, so its `0x1` says nothing about it.

### 3.17 Measured for stage 4a

From `inotify-delivery-probe.c` (output beside it), Linux 6.18.5 aarch64, as
root and as uid 1000, run twice with identical output:

- **`utimensat`** (V) of both times, or with a null `times`, is `IN_ATTRIB`;
  of the access time alone `IN_ACCESS`, and of the modification time alone
  `IN_MODIFY` (`UTIME_NOW` or a time alike); of neither, nothing. A watch
  asking for the `FileSystemWatcher` mask, which has no `IN_ACCESS`, hears
  nothing of the access time alone.
- **Set-ID bits** (Z, uid 1000): `truncate(2)` and `open(O_TRUNC)` of a 06755
  file leave 0755 and queue **one** record, `MODIFY+ATTRIB`, which a queue one
  short of full takes without overflowing; root's `chown` likewise one
  `IN_ATTRIB`. A `write` that clears them is two records, `IN_ATTRIB` then
  `IN_MODIFY`, and overflows that queue. Under a watch asking for
  `IN_MODIFY` alone, or `IN_ATTRIB` alone, the `O_TRUNC` record still carries
  `MODIFY+ATTRIB`: a watch's mask decides whether a record is queued, not
  which bits it carries. A write through a name since unlinked that clears
  them, under a watch on the old directory with `IN_EXCL_UNLINK`, queues
  `IN_ATTRIB` under the old name and no `IN_MODIFY`.
- **An inode watched beside its parent** (Y), by one instance: the parent's
  record, with the name, then the inode's own, for `chmod`, `truncate`,
  `O_TRUNC` and `utimensat` alike; a second instance on the parent hears too.
- **Link counts** (X): `link` and `unlink` of another name of a watched file
  queue `IN_ATTRIB` at the file's own watch, then `IN_CREATE` or `IN_DELETE`
  at the parent's, and nothing with the name; `mkdir` and `rmdir` in a watched
  directory queue only the entry's record, though its link count moves.
- **The displaced inode of a rename** (R): `IN_MOVED_FROM`, `IN_MOVED_TO`, then
  `IN_ATTRIB` at the displaced inode's own watch (`ATTRIB+ISDIR` for an empty
  directory), then, once it is forgotten, its `IN_DELETE_SELF` and
  `IN_IGNORED` (at once if nothing holds it; at the close of a descriptor
  that does).
- **Which name** (P): through a symbolic link, the target's directory and
  name; "d/." and "e/.." the directory's own parent and name; "d/e/" `e`. A
  mount point (`/dev`) is heard at its own watch alone, not at `/`'s. A
  directory `rmdir` removed while it was the current directory, changed
  through ".", is heard at its own watch **and at its old parent's, under its
  old name**.
- **`open`** (T): `O_CREAT|O_TRUNC` of a new file is `IN_CREATE` alone;
  `O_CREAT` of an existing file nothing; `O_TRUNC` of an existing file, empty
  or not, and with `O_RDONLY`, `IN_MODIFY`.
- **Changes of nothing** (C): `chown` naming neither ID queues nothing; naming
  the IDs the file has, or only its user, `IN_ATTRIB`; `chmod` to the mode it
  has, `IN_ATTRIB`.
- **Another process** (M): the records of changes a child makes are those the
  same changes make in the reading process.

### 3.18 Measured for stage 4b

From `inotify-dentry-probe.c` (output beside it), Linux 6.18.5 aarch64, as
root, run twice with identical output:

- **`IN_EXCL_UNLINK`** (E), with a file unlinked while open: a watch with it,
  on the old directory **or on the file itself**, hears nothing of `write`,
  `pwrite` or `copy_file_range` through the descriptor, and hears
  `ftruncate`'s `IN_MODIFY` and the `IN_ATTRIB` of `fchmod`, `fchown`,
  `futimens`, and `utimensat`, `fchmodat` and `fchownat` of the empty path
  under `AT_EMPTY_PATH`. So the flag keeps out the events Linux raises with
  the file's path (`fsnotify_modify`), not a `setattr`'s (`fsnotify_change`,
  which carries the dentry alone); 4a's reading of the source was right.
  Without the flag, every one is heard at the old directory under the old
  name, and at the file's own watch.
- **A name given again** (L): after `unlink("l/b")` and `link("l/a",
  "l/b")`, a write through the descriptor opened as `b` is kept out of a
  watch with `IN_EXCL_UNLINK`, and one through a fresh `open("l/b")` is not:
  the name given again is another dentry, and the old stays unlinked though
  its directory binds the name to the same inode again.
- **A name renamed over** (O): a descriptor opened through `t`, after
  `rename("o/s", "o/t")`, writes as through an unlinked name (`MODIFY "t"`
  without the flag, nothing with it); its `fchmod` is heard either way.
- **A directory's descriptor** (Q): `fchmod` through it is heard under its
  name as renamed and moved (`d2` at `q`, then `d3` at `other`), and after
  `rmdir` under its old name at its old parent, with or without
  `IN_EXCL_UNLINK`; `futimens` alike.
- **The directory of an unlinked name** (U): with `u/sub/f` open and
  unlinked, `rmdir("u/sub")` queues `DELETE|ISDIR "sub"` at `u` and nothing
  at `sub`'s own watch, a write through the file then queues
  `MODIFY "f"` at `sub`'s watch, and only the file's `close` queues `sub`'s
  `DELETE_SELF` and `IGNORED`: the dentry holds its parent.
- **A device** (V): a write to `/dev/null` under a watch on `/dev`
  (devtmpfs) queues nothing.
- **The Kestrel handoff** (K), under `FileSystemWatcher`'s mask:
  `File.WriteAllText("server-address.tmp")` is `CREATE` then `MODIFY` of the
  name, and `File.Move` to `server-address` (`rename(2)`, the destination
  being absent) the `MOVED_FROM`/`MOVED_TO` pair.

### 3.19 Measured for stage 4c

From `inotify-self-probe.c` (output beside it), Linux 6.18.5 aarch64, as
root, run three times in three container boots with identical output:

- **When a watched inode goes.** Linux queues `IN_DELETE_SELF` and
  `IN_IGNORED`, and drops the watch, when a name of the inode dies while
  the inode has no link left: an unlink, `rmdir` or rename displacing it
  from a name nothing holds, or the release of the last thing holding a
  name already unlinked (Linux's dentry, which a descriptor opened through
  it, a current directory, or a name in a directory holds). That is not
  when the inode itself goes:
  - a file opened through `a`, `a` unlinked, then its other name `b`
    unlinked (or renamed over): the records come at the unlink of `b`,
    though the descriptor still holds the file (N one, N rename-over);
  - opened through `a` and through `b`, both unlinked: at the first close
    (N two); through `a` twice: at the second (N same);
  - opened through `b`, `b` unlinked and linked again, opened through `b`
    again, then every name unlinked: at the close of the first
    descriptor, though the second was opened through the same name (N
    relinked). A name given again is another name, as 3.18's L found for
    `IN_EXCL_UNLINK`.
  A directory has one name, so for a directory the two coincide: its
  watch goes when the directory does, at the `rmdir`, at the close of a
  descriptor onto it, or when the last process standing in it leaves (D
  held, D cwd); a chain of removed directories held by the innermost goes
  innermost first (D chain).
- **Order.** `unlink` of a watched file's last name, nothing holding it:
  the file's `IN_ATTRIB` (its link count), `IN_DELETE_SELF`, `IN_IGNORED`,
  then the directory's `IN_DELETE` (U), as `rmdir`'s child-before-parent
  (3.5). A rename: `IN_MOVED_FROM`, `IN_MOVED_TO`, the displaced inode's
  `IN_ATTRIB`, the moved inode's `IN_MOVE_SELF`, then the displaced
  inode's `IN_DELETE_SELF` and `IN_IGNORED` (R).
- **`IN_MOVE_SELF`** comes for a rename of any name of the inode (R
  other-name-of-watched), and not for a rename onto another name of the
  same inode, or onto itself, which change nothing. A watch not asking for
  it hears nothing. Neither self event carries `IN_ISDIR`, for a directory
  either.
- **A watch not asking for `IN_DELETE_SELF`** gets `IN_IGNORED` alone (U,
  and D dotnet: under `FileSystemWatcher`'s mask, `rmdir` of a watched
  subdirectory queues the child's `IN_IGNORED` and then the parent's
  `DELETE|ISDIR`).
- **Afterwards** `inotify_rm_watch` of the watch is `EINVAL`, and adding a
  watch on a file created under the old name gives a fresh descriptor (U).
- **Two instances** each hear of the going on their own queue (W).
- **Another process's exit** (X): a process holding `a` through two
  descriptors and `b` through one, between them, both unlinked, exits;
  Linux releases its files after closing every descriptor, the last let go
  of first, and `a`'s name is held until its first descriptor's file is
  released, so `b` goes first. A file that is let go of is still a
  reference until its release.
- **The queue limit** applies to both records, and the watch goes whether
  or not its `IN_IGNORED` was queued: one short of full, `IN_DELETE_SELF`
  takes the last place and `IN_IGNORED` becomes the `IN_Q_OVERFLOW` record
  (Q).

## 4. Design

### 4.1 Where the instance lives

- **(a) In the open file description**: `OpenFileTarget.Inotify of InotifyState`,
  as `Epoll of EpollState`. The instance is its description: `inotify_init1`
  makes one, `dup` shares it (3.11), it dies with its last reference, and no
  syscall names it except through a descriptor. Its watches, queue, next wd and
  overflow flag are in the state.
- **(b) A machine table** `Inotify : Map<InotifyId, InotifyState>` with the
  target holding the id, as sockets and pipes are kept. Those need it because
  a socket precedes its description (`accept`) and a pipe outlives either
  end's. An inotify instance does neither, so (b) adds a lifetime rule and
  invariant clauses for nothing.
- **(c) Marks on the inode**, as Linux keeps `i_fsnotify_marks`: each `Inode`
  carries `Map<OpenFileDescriptionId, mask>`. Emission is then a lookup on the
  inode, but `VirtualFileSystem`, a pure graph that knows nothing of
  descriptions, would hold references into the open file table, every mark
  change would be a filesystem change, and `forget` would have to reach the
  queues. Rejected.

**Recommend (a).** With it, "which instances watch inode *i*" is a scan of
`OpenFiles` for `Inotify` targets holding a watch on *i*, once per emitted
event. The table is tens of entries in a Kestrel run and file writes are
rare, so a per-inode index on the machine (`Map<InodeNumber, Set<OpenFileDescriptionId>>`,
with an invariant tying it to the watches) is the upgrade if the scan ever
shows in a profile, not the first version.

The per-user limits (3.12) are derived the same way: the instance records the
`UserId` that created it, and `inotify_init1` and `inotify_add_watch` count
instances and watches of that user by scanning, rather than keeping a second
count that could disagree.

### 4.2 How a filesystem change becomes events

Every event in 3.3 to 3.6 except `OPEN`, `CLOSE_*` and `ACCESS` is a change to
the inode graph. Three ways to produce them:

- **(1) Hook each syscall.** Each of the ~25 sites that stores a new
  `FileSystem` also calls `Inotify.notify` with the records it knows it caused.
  A forgotten site is silent: the change happens and no watcher hears it, and
  nothing but a guest can tell.
- **(2) Diff the graph.** After each syscall, compare the `VirtualFileSystem`
  before and after and derive the records. It cannot pair a `MOVED_FROM` with
  its `MOVED_TO` (a diff sees a name gone and a name arrived), cannot order the
  records of one syscall (3.5's child-before-parent), cannot say which name a
  `write` went through (3.6), and cannot see `OPEN`/`CLOSE`/`ACCESS` at all. It
  is, however, an excellent *oracle* for the structural records.
- **(3) The mutation reports what it did.** Each `VirtualFileSystem` mutator
  returns, beside the new graph, the `FsChange`s it made:

  ```fsharp
  type internal FsChange =
      | EntryAdded of directory : InodeNumber * name : DirectoryEntryName * inode : InodeNumber
      | EntryRemoved of directory : InodeNumber * name : DirectoryEntryName * inode : InodeNumber
      | EntryMoved of
          source : InodeNumber * DirectoryEntryName *
          destination : InodeNumber * DirectoryEntryName *
          inode : InodeNumber * displaced : InodeNumber option
      | ContentChanged of inode : InodeNumber
      | AttributesChanged of inode : InodeNumber     // mode, owner, times, link count
      | InodeForgotten of inode : InodeNumber
  ```

  One function, `InotifyDelivery.ofChanges`, turns a change list into records
  for every instance watching the inodes involved (`ISDIR` from the inode's
  content), and that function is the only producer. The mutators are the
  twelve places that know exactly what changed, and the change list has an
  independent oracle: for every mutator and every input, `FsChange.ofDiff before after`
  must agree with the list it returned (set equality, ignoring order and
  `displaced`), which is (2) put to its proper use.

  The remaining question is how to stop a site storing a graph without its
  changes. Today the field is `UnixMachineState.FileSystem : VirtualFileSystem`,
  so `{ machine with FileSystem = vfs }` compiles anywhere in the library.
  Give the field a type whose representation is private to one file:

  ```fsharp
  // FileSystemCommit.fs, after FileDescriptorRegistry.fs and before UnixMachine.fs
  type internal CommittedFileSystem = private { Graph : VirtualFileSystem }
  module internal CommittedFileSystem =
      let graph : CommittedFileSystem -> VirtualFileSystem
      let initial : VirtualFileSystem -> CommittedFileSystem        // boot only
      /// Store `mutation.After`, and queue its changes on every inotify instance in `openFiles`.
      let commit : Dentry option -> VfsMutation -> OpenFileTable -> CommittedFileSystem -> CommittedFileSystem * OpenFileTable
  ```

  `VfsMutation = { After : VirtualFileSystem; Changes : FsChange list }` is
  what every mutator returns. No file but `FileSystemCommit.fs` can build a
  `CommittedFileSystem`, so no graph reaches the machine without `commit`,
  which is where delivery happens. The ~25 sites become calls to one
  `UnixMachineState.commitFileSystem` helper, a mechanical change the compiler
  drives. `Dentry option` is the name the operation went through (4.3), for
  `ContentChanged` and `AttributesChanged`, which have no name of their own.

  If the private representation turns out to fight some site (a boot-time
  seed, `forget`), the fallback is a `scripts/check-*.py` ratchet that fails
  on any `FileSystem =` outside that file, as `check-pal-residue.py` does for
  PAL encodings.

  **As built in stage 2.** The private representation did not fight any site,
  so there is no ratchet. What stage 2 settled beyond the sketch above:

  - `VfsMutation` has a private representation too, in `VirtualFileSystem.fs`,
    read through `VfsMutation.before`, `after` and `changes`, so that a change
    list cannot be forged beside a graph either. It carries the graph it was
    made from, and `commit` refuses a mutation not made from the graph it
    holds (by reference), which is a lost update.
  - `commit` is `VfsMutation -> CommittedFileSystem -> CommittedFileSystem`
    for now; the `Dentry option` and the `OpenFileTable` arrive with
    delivery. The machine's field is `CommittedFileSystem`, and
    `UnixMachineState.FileSystem` is a member reading its graph, so the
    readers did not change. `CommittedFileSystem.initial` remains the one
    way to install an arbitrary graph: `UnixSystem.initial` and
    `UnixBootImage.withFileSystem` call it, and so do tests that forge a
    machine. Nothing but review stops a library site calling it.
  - The boot builders (`empty`, `ofFileSystemSeed`, `mountAtRoot`) still
    answer a graph; the thirteen mutators answer a `VfsMutation`. Eighteen
    calls commit, two of them in `chown`, which commits the owner and then
    the stripped mode as two mutations.
  - What each reports: a creation (`createFile`, `createDirectory`,
    `createSymlink`, `cloneFile`) `EntryAdded`; `hardLink`
    `AttributesChanged` of the target and then `EntryAdded`; `unbind`
    `EntryRemoved`, preceded by `AttributesChanged` for an inode that is no
    directory (its lost link; Linux's `rmdir` notifies no attribute change);
    `rename` one `EntryMoved`, whose `displaced` is also that inode's lost
    link; `writeFile` and `truncateFile` `ContentChanged`, preceded by
    `AttributesChanged` when they strip a set-ID bit; `setPermissions`,
    `setOwner` and `setTimes` `AttributesChanged`; `forget`
    `InodeForgotten`. A directory's stamps and link count under an entry
    change are part of that change, not an `AttributesChanged`.
  - The diff oracle is `FsChangeDiff` in `TestFsChange.fs`, not library code.
    It holds names and forgotten inodes to the diff exactly (a rename as its
    removed and added names, and its displaced inode's removed name), what
    the diff names for certain (bytes, mode, owner, a non-directory's link
    count) as reported, every reported content or attribute change as
    visible, and every inode that changed at all as named by some reported
    change. It cannot tell a rename from a removal and an addition, order,
    or a truncation to the same length from a stamp alone.

  **As built in stage 4a.** `commit` is
  `ChangeNotice -> int -> VfsMutation -> OpenFileTable -> CommittedFileSystem -> CommittedFileSystem * OpenFileTable`,
  the `int` being the instances' queue limit, and `UnixMachineState.commitFileSystem`
  is `ChangeNotice -> VfsMutation -> UnixMachineState -> UnixMachineState`.
  What 4a settled beyond the sketch:

  - A `Dentry option` alone could not say what a change raises, so the
    notice says how the syscall reached what it changed (`InotifyDelivery.fs`):
    `ChangeNotice.Names` for a change of names, whose `AttributesChanged` are
    link counts, reported at the inode's own watch alone (3.17, X);
    `ChangeNotice.SetAttributes (through, set)` for `chmod`, `chown`,
    `utimensat` and a truncation, where `set : AttributesSet` is what Linux's
    `fsnotify_change` reads of `ia_valid` (mode, owner, size, access time,
    modification time) and `through` is a `ReachedThrough` (`Path of Dentry
    option`, `RemovedDirectory of oldParent`, `Descriptor`); and
    `ChangeNotice.Written` for a write.
    `AttributesSet.events` is that function's rule, which neither `FsChange`
    nor a dentry could give: one time alone is `IN_ACCESS` or `IN_MODIFY`, and
    `chown` naming no ID moves `ctime` and raises nothing (3.17).
  - `Dentry = { Parent; Name }` (`Dentry.fs`), with no `Unlinked` yet, which
    4b adds. `ReachedThrough.ofResolved` takes it from the walk's final
    entry, or for a path ending at a directory by ".", ".." or "/" from the
    directory's own name in its parent; `None` at the root and at a mounted
    root. A directory whose last name has gone is `RemovedDirectory`: Linux
    names it to its old parent (3.17, P), which its `..` still is, under a
    name the graph does not keep.
  - **Refused, not dropped.** Where Linux reports an event through a name
    this kernel does not keep, `commit` answers an `UnplacedChangeRefusal`
    (`DescriptorName`, `RemovedDirectoryName`; `InotifyDelivery.unplacedRefusal`)
    if a watch asking for the event could be the one it reaches, and commits
    otherwise, so that a machine with no relevant watch is unaffected. Each
    syscall that can reach one carries it as its own refusal's
    `UnplacedChange` case, of kind `Unmodelled`, which its public entry
    point raises as `UnmodelledException` (the skill's §5); a change of
    names goes through `commitFileSystem`, which is never refused. Through a
    descriptor (until 4b records `OpenedThrough`): a watch on the inode, or on
    any directory, since the name the descriptor was opened through may have
    been unlinked while another survives (found by Codex: section H's
    write-via-b-after-unlink-of-b), but for a write's `IN_MODIFY` a watch
    with `IN_EXCL_UNLINK` on a directory not naming the file (row D
    write-unlinked-excl-unlink; the `IN_ATTRIB` of set-ID bits a write
    clears is not kept out, measured as 3.17's row Z
    write-unlinked-excl-unlink, found by Codex); for a directory's
    descriptor, its parent.
    Broad, and honest until 4b. Through a
    removed directory: a watch on its old parent. A write's events are
    `IN_MODIFY`, and `IN_ATTRIB` for set-ID bits it clears.
  - One syscall, one notice, one record: `chown`'s owner and its cleared
    set-ID bits are one mutation (`VfsMutation.andThen`), as a truncation's
    size and cleared bits already were, and `SetAttributes` makes one record
    of all its changes (3.17, Z, at a queue one short of full).
  - `InotifyDelivery.notifications` turns a mutation and its notice into
    Linux's events in order (`InotifyNotification`, the watched inode and the
    events), and `InotifyDelivery.deliver` queues each on every instance
    watching that inode whose watch asks for any of its events, as one record
    carrying them all, instances in the order of their description IDs. The cookie counter is in
    `CommittedFileSystem`, so nothing but `commit` advances it; it starts at 1
    and wraps.
  - The plan's `truncate(path)` is not in this kernel: there is no
    `truncate(2)`. `O_TRUNC` is the path-based truncation.

  **As built in stage 4c.** `InotifyDelivery.notifications` answers
  `InotifyEffect`s, a notification or `WatchesEnd` of an inode, which
  `deliver` makes by removing each watch on it and then queueing its
  `IN_DELETE_SELF` (if asked) and `IN_IGNORED`. 3.19 found that Linux ends
  the watches when a name of the inode dies with no link left, not when the
  inode goes, so the plan's `InodeForgotten` is one of three triggers:
  - a change of names whose removal (`EntryRemoved`, or a rename's
    `displaced`) leaves a non-directory no link, through a name no
    description records still linked (`OpenFileTable.holdsLinkedName`);
  - `ChangeNotice.NameReleased`, which `ObjectLifetime.releaseDestroyed`
    commits, with `VirtualFileSystem.unchanged`, when it releases the last
    description holding a name of a file since unlinked. Which descriptions
    hold one name is the open file table's `NameIdentity`: a description
    opened through a linked name that a live one records shares its
    identity, and a name linked again is another (3.19, N relinked), so the
    walk's record alone could not say. `FileDescriptorRegistryDefect.OpenedThroughNameNotShared`
    holds the table to that;
  - `InodeForgotten`, the only one a directory reaches, since a directory
    has one name, held while anything pins it.
  The going of an inode whose name the change removed comes before that
  removal's `IN_DELETE`, and after a rename's `IN_MOVE_SELF`. For the
  forgetting to be in the same change as the removal, `unlink`, `rmdir` and
  `rename` commit through `ObjectLifetime.commitRemoving`, which adds
  `VirtualFileSystem.forget` to the mutation when nothing will hold the
  inode. No delivery happens outside `commit`. At a Linux process's end,
  `SimulatedMachine.endProcess` holds each description its drops let go of
  until that description's turn to be released, as Linux's deferred `fput`
  keeps the file, so that a release sees the names its batch still holds
  (3.19, X).

**Recommend (3)**, with (2) as its property-test oracle. Each site in (1)
would have had to restate what the mutator already knew, and only a guest
could catch one that restated it wrongly or not at all. `OPEN`, `CLOSE_*` and
`ACCESS`, which are not graph changes, stay out of scope (4.4); if they are
ever modelled they are hooks in `open`, the description's destruction and
`read`, and (1) is the right shape for exactly those three.

### 4.3 The name a descriptor was opened through

3.6 shows that an event raised through a descriptor goes to the parent of the
*dentry* the descriptor was opened through, under that dentry's current name,
and 3.5 that `IN_EXCL_UNLINK` suppresses it once that dentry is unlinked. The
model has no dentries.

- **(a) Record the dentry on the description.** `OpenFileTarget.File` and
  `Directory` gain `OpenedThrough : Dentry option`, where
  `Dentry = { Parent : InodeNumber; Name : DirectoryEntryName; Unlinked : bool }`,
  filled from the path walk's `ResolvedTarget.Entry (directory, name, _)` at
  `open`, `None` for a description that no path made (a launch descriptor).
  `rename` of exactly that `(Parent, Name)` onto an inode that is the
  description's rewrites every matching description's dentry to the new pair
  (`d_move`); `unlink` of it sets `Unlinked`. A fresh file taking the old name
  later is a different dentry, which is why `Unlinked` is stored rather than
  derived from "does the parent still bind the name to this inode".
  `checkInvariants` gains: a dentry not `Unlinked` names its inode in its
  parent; an `Unlinked` dentry does not.
- **(b) A dentry cache.** A machine table of `DentryId`s with parent, name and
  inode; directory entries become `Map<DirectoryEntryName, DentryId>`;
  descriptions hold a `DentryId`. The faithful model, and it would also serve
  the orphaned-directory `..` bookkeeping `ObjectLifetime.pinnedInodes` does by
  climbing. But it rewrites `VirtualFileSystem`'s core type and every walk over
  it for one consumer.
- **(c) Record nothing, and refuse** `ContentChanged`/`AttributesChanged`
  delivery for descriptor-based operations whenever some instance watches the
  file's parent. The Kestrel handoff is `write(fd)` into the watched directory,
  so this refuses the goal.

**Recommend (a).** Every row of 3.6 is one of its three rules, and the invariant
keeps it honest. (b) is the upgrade if a second consumer of dentries appears.

**As built in stage 4b.** `OpenFileTarget` is public, and changing a public
union's case is a major version, so the record is not on `File` and
`Directory` but on the open file table's private entry (`OpenFileEntry`),
beside the descriptor and hold counts, read with `OpenFileTable.openedThrough`.
It is made with the description: `openFile`, `openDirectory` and
`openCharacterDevice` take it, `OpenFileTable.create` refuses loudly a
description onto an inode without one or another with one, and
`FileDescriptorRegistryDefect.OpenedThroughMismatch` says the same of the
table. What settled beyond the sketch:

- The record is the walk's `ReachedThrough` (`Dentry.fs`), which 4b reshaped
  to `Name of Dentry * unlinked`, `Unnamed` (the root, or a mounted root) and
  `RemovedDirectory of oldParent`, and whose `Descriptor` case went: a
  descriptor now says how it was reached. `Unlinked` is a flag on `Name`
  rather than a field of `Dentry`, since a walk never reaches an unlinked
  name. A device's node records one too, as does a FIFO's when FIFOs exist.
- `CommittedFileSystem.commit` moves and marks the records
  (`OpenFileTable.followChanges`, by `ReachedThrough.followChange`) from the
  mutation's `FsChange`s, so no syscall can forget to: `EntryMoved` of exactly
  that name onto the description's inode moves it; `EntryRemoved` of it, or
  an `EntryMoved` displacing the inode from it, marks it unlinked. A record
  already unlinked stays as it is.
- The plan's second clause ("an `Unlinked` dentry does not name its inode in
  its parent") is false, measured (3.18, L): a name linked again to the same
  inode leaves the old record unlinked, as Linux does. `checkInvariants`
  states instead: a name not unlinked is bound to the description's inode in
  its directory (`OpenedThroughNameUnbound`); an unlinked one's directory is
  in the graph (`OpenedThroughParentGone`); `Unnamed` is the root or a mounted
  root (`OpenedThroughNoNameNotRoot`); `RemovedDirectory` is a directory whose
  ".." is that parent and which it no longer names
  (`OpenedThroughRemovedDirectoryNamed`).
- The name holds its directory (`UnixMachineState.heldInodes`), as a dentry
  holds its parent (3.18, U), and releasing the description forgets that
  directory if nothing else holds it.
- `IN_EXCL_UNLINK` is `InotifyNotification.HiddenByExclUnlink`: set on a
  write's `IN_MODIFY` through an unlinked name, at the directory's watch and
  the inode's own, and on nothing else (3.18, E).
- What stays refused is a change to a directory reached by "." after its
  `rmdir`, by a path or by a descriptor opened that way, whose old name the
  graph does not keep: `UnplacedChangeRefusal.RemovedDirectoryName`, now its
  only case. A directory opened through its name before its `rmdir` keeps
  that name, and is heard (3.18, Q). `DescriptorName`, `Unplaced.ThroughDescriptor`,
  and the `UnplacedChange` cases of `WriteRefusal`, `PWriteRefusal`,
  `CopyFileRangeRefusal` and `TruncationRefusal` went, since a write and a
  truncation are of a regular file, which only a name reaches; they commit
  through `UnixMachineState.commitFileSystem`, which fails loudly if refused.

### 4.4 Which events and flags, and what is refused by name

**Modelled.** Events: `IN_CREATE`, `IN_DELETE`, `IN_MOVED_FROM`, `IN_MOVED_TO`,
`IN_MODIFY`, `IN_ATTRIB`, `IN_DELETE_SELF`, `IN_MOVE_SELF`; the kernel-added
bits `IN_ISDIR`, `IN_IGNORED`, `IN_Q_OVERFLOW`. Flags: `IN_ONLYDIR`,
`IN_DONT_FOLLOW`, `IN_EXCL_UNLINK`, `IN_MASK_ADD`, `IN_MASK_CREATE`. These are
every bit the `FileSystemWatcher` mask carries, plus the self events, which
cost nothing once `InodeForgotten` and `EntryMoved` exist and which 3.4 and
3.5 measure.

**Refused by name**, in `inotify_add_watch`, before anything changes, where
the call would otherwise succeed (a call that fails answers its errno)
(`InotifyAddWatchRefusal.UnmodelledEvents of InotifyEvent list`, and
`InotifyAddWatchRefusal.OneShot`):
`IN_ACCESS`, `IN_OPEN`, `IN_CLOSE_WRITE`, `IN_CLOSE_NOWRITE` (not graph changes;
4.2), `IN_ONESHOT` (nothing on the path uses it), `IN_UNMOUNT` (nothing
unmounts). A refused bit is never dropped silently: a hand-rolled guest
asking for `IN_ALL_EVENTS` is told which bits it cannot have. The
`inotify_init1` flags are `IN_CLOEXEC` and `IN_NONBLOCK`, in the flavour's
`<fcntl.h>` numbering (`OpenFlagNumbering`); any other bit is `EINVAL`, as
Linux answers.

The mask crosses the API raw (`uint32`, Linux's `<sys/inotify.h>` numbering),
as `open`'s flag word does, and is parsed inside into an `InotifyMask` of
typed events and flags. The record a `read` returns is bytes laid out as 3.7
(`InotifyRecord.toBytes`), because the layout is the kernel's ABI, not a
client's encoding.

### 4.5 The queue

`InotifyState`:

```fsharp
type InotifyState =
    { Owner : UserId                                  // for the per-user limits
      Watches : Map<WatchDescriptor, InotifyWatch>    // InotifyWatch = { Inode; Mask : InotifyMask }
      NextWatchDescriptor : int                       // starts at 1, never reused (3.2)
      Queue : InotifyRecord list                      // oldest first; at most MaxQueuedEvents + 1
    }
```

- **Append** (`InotifyQueue.enqueue`), in Linux's order (3.16): if the queue
  holds `max_queued_events` records (the overflow record counted), drop the
  record, and append `IN_Q_OVERFLOW` (wd -1, cookie 0, no name) unless one is
  queued; else drop it if it repeats the newest record, comparing watch, mask
  and name but not the cookie (3.8, 3.16); else append. The property tests
  state: length at most max + 1, and at most one overflow record, which is
  last unless reads have made room since (3.16).
- **`inotify_rm_watch`** removes the watch and appends `IN_IGNORED` for its wd
  (3.2, 3.13). **`InodeForgotten`** of a watched inode appends `IN_DELETE_SELF`
  (if asked) then `IN_IGNORED`, and removes the watch (3.4). A watch on an
  inode the graph has forgotten is a `checkInvariants` defect
  (`UnixSystemDefect.InotifyWatchOfForgottenInode`). As built, a name's
  death does this too, as 3.19 measured (4.2, as built in stage 4c).
- **Cookies**: a machine counter `NextInotifyCookie : uint32` starting at 1,
  taken by every `EntryMoved` whether or not anything watches either directory
  (Linux's `fsnotify_get_cookie` is global and unconditional; 3.11 shows
  adjacent renames one apart). Only equality of the two halves is observable in
  practice.
- **Order within one syscall** is the order of the change list: `rename`
  reports `EntryMoved` as one change, delivered as `MOVED_FROM` then
  `MOVED_TO` at the directories' watches and then `MOVE_SELF` at the inode's
  (3.5); `rmdir` reports `EntryRemoved` and, when nothing else holds the
  directory, `InodeForgotten`, and delivery puts the forgotten inode's
  `DELETE_SELF` and `IGNORED` before the parent's `DELETE|ISDIR`, as measured.
  That order is a rule of `InotifyDelivery.ofChanges`, pinned by the replayed
  probe row, not of the change list.
- **`IN_EXCL_UNLINK`** on the parent's watch suppresses a delivery whose dentry
  is `Unlinked` (3.5). Without it the delivery carries the old name. As
  measured for 4b (3.18, E), it suppresses only a write's `IN_MODIFY`, and at
  the inode's own watch as well as the parent's.
- **`IN_ISDIR`** is set when the subject inode is a directory, including on
  events about the watched directory itself (3.3's `chmod` row).

### 4.6 Reading, readiness and waking

- **`read`**: the target `ReadTarget.Inotify (description, nonBlocking)`.
  With the queue empty: `EAGAIN` if non-blocking (count 0 included), else park
  `ParkedSyscall.InotifyRead of ParkedInotifyRead` holding the description.
  With a record queued: `EINVAL` if `count` is less than the first record's
  size (count 0 included); otherwise as many whole records as fit, oldest
  first, taken off the queue. An unmapped buffer is `EFAULT` **and the first
  record is dropped** (3.9): modelled, since it is measured and costs one
  line (decision 5). A write is `EBADF`, from the `ReadOnly` access
  mode `inotify_init1` gives the description (3.1), with no inotify-specific
  arm.
- **Wake**: `WakePrimitive.InotifyRecordQueued of reader : OpenFileDescriptionId`,
  which holds when the queue is non-empty; every parked reader on the
  instance wakes (non-exclusive, 3.15), and `finishRead` answers as above or
  re-parks; a record beats a signal, and a description made non-blocking
  while the read slept answers `EAGAIN` (3.16). A signal interrupts as every
  park does, and `SA_RESTART` restarts. Linux's `close` never ends
  the read (3.13): the park holds the description, exactly as `PipeRead` does.
- **Readiness**: `LinuxReadiness.ofDescription` answers `EPOLLIN|EPOLLRDNORM`
  while the queue is non-empty (3.10, 3.16), never `OUT`. `epoll_ctl` admits
  the target. Every record the queue takes (not one it drops) wakes the
  instance's epoll registrations, unkeyed (3.16); it goes through
  `OpenFileTable.enqueueInotify`, so nothing else has to remember it.
- **`FIONREAD`** is the queued bytes; **`lseek`** answers 0 for everything;
  **`fstat`** is `FStatRefusal.EventQueue`, as for epoll; the `flock` object
  is `AnonymousInode` (3.1).
- **Cross-process**: a change committed in process A's view appends to an
  instance B owns, in the shared `OpenFiles`; `SimulatedMachine.wakes` then
  finds B's park satisfied. Nothing new is needed beyond (a) of 4.1; section 5
  tests it.

### 4.7 The limits are configuration

`fs.inotify.max_user_instances` (128), `fs.inotify.max_queued_events` (16384)
and `fs.inotify.max_user_watches` (derived from the machine's memory: 8982 in
a 1 GiB VM; Linux clamps it to [8192, 1048576]) are sysctls an administrator
sets, so they are `UnixBootImage.withInotifyLimits` with a refusal for a
non-positive value, and `MachineConfig.InotifyLimits : InotifyLimits option`
on PawPrint's side. Defaults: 128, 16384, and **8192** for watches, the
documented floor every real machine meets. `EMFILE` past the instance limit
and `ENOSPC` past the watch limit, counted per `Owner` across every process on
the machine (4.1). `FileSystemWatcher` reads `/proc/sys/fs/inotify/*` only on
those errors; the paths do not exist in the model and the read fails
harmlessly inside its `try`.

### 4.8 Flavour

inotify is Linux's. Under the Darwin flavour, `inotifyInit1`,
`inotifyAddWatch` and `inotifyRmWatch` are refused
(`InotifyRefusal.Flavour of SimulatedUnixFlavour`), as `epoll_ctl` is: no
Darwin kernel has the call, so there is no measured answer. The Darwin
CoreLib never makes these calls; its watcher is FSEvents, which PawPrint does
not model and which `NativeCall.failUnimplemented` already names
(`CoreServices!FSEventStreamCreate`) when a guest reaches it. No by-name
refusal is added for it: the generic failure says what is missing, and a
guest wanting a watcher on the Darwin flavour sets
`DOTNET_USE_POLLING_FILE_WATCHER=1`. The Linux pack
(`$DOTNET_LINUX_FRAMEWORK_DIR`) is the target, and `TestAspNetTwoProcess`
already runs on it alone.

### 4.9 PawPrint's side

- Handlers in `NativeSystemNative.fs`: `SystemNative_INotifyInit` calls
  `UnixInotify.inotifyInit1` with the flavour's `IN_CLOEXEC`;
  `SystemNative_INotifyAddWatch(fd, path, mask)` reads the UTF-8 path and the
  mask; `SystemNative_INotifyRemoveWatch(fd, wd)`. Errors go through errno as
  every handler's do. The shim is a verbatim pass-through on Linux
  (`pal_io.c:1461-1501`, with `IN_EXCL_UNLINK` kept because `HAVE_IN_EXCL_UNLINK`).
- `Native/NotifyEventsPal.fs`: the PAL `NotifyEvents` numbering to the kernel's
  raw mask. The values are identical (`pal_io.c:180-196` asserts each
  `PAL_IN_*` equals `IN_*`), and the adapter still exists, because the rule is
  that a PAL encoding is converted in `Native/`, and so that
  `check-pal-residue.py` has a name to see.
- `SystemNative_Read` gains the `ParkedSyscall.InotifyRead` re-entry arm
  beside `PipeRead`; `SystemNative_Poll` and `SystemNative_GetBytesAvailable`
  need nothing once the kernel answers for the target.
- **The test's current directory.** With the content root at `/`,
  `FileSystemWatcher`'s `Directory.EnumerateDirectories("/")` finds `dev`,
  watches it (fine) and then enumerates it, which the kernel refuses, and
  under PawPrint a refusal is a host failure that ends the run. Two ways out:
  model listing the devtmpfs, or give the processes a current directory that is
  not `/`. **Recommend the latter**: `TestAspNetTwoProcess` seeds `/app` and
  sets `ProcessConfig.CurrentDirectory` to it for both guests, as
  `TestImpureCases.currentDirectoryCase` already does for one. The handoff
  name is relative on both sides; the oracle's scratch directory, which holds
  a `0/` and a `1/` per guest, is watched recursively by the real server and
  nothing writes into those. Real applications never run from `/` either.
- Then the `DOTNET_USE_POLLING_FILE_WATCHER` entry and the docstring bullet
  that explains it go.

## 8. Decisions

Patrick took each recommendation on 2026-10-11; they are settled.

1. **Delivery (4.2): (3)**, the mutators report `FsChange`s and one
   `commit` delivers them, with the diff as the oracle; the private
   representation is the enforcement, a check script the fallback.
2. **Where the instance lives (4.1): (a)**, in the description, with a scan
   for watchers and per-user counts derived by scanning; the per-inode index
   only if measured slow.
3. **The dentry (4.3): (a)**, `OpenedThrough` on file and directory
   descriptions, moved by `rename` and marked by `unlink`; a dentry cache
   only for a second consumer.
4. **Scope (4.4):** refuse `IN_ACCESS`, `IN_OPEN`, `IN_CLOSE_*`, `IN_ONESHOT`,
   `IN_UNMOUNT` by name; model the self events.
5. **The `EFAULT` row (4.6):** model the lost record, since it is measured,
   rather than refuse `UserBuffer.Unmapped` on an inotify read.
6. **Limits (4.7):** boot configuration with defaults 128, 8192, 16384.
7. **Darwin (4.8):** the kernel refuses by flavour; PawPrint adds no by-name
   refusal for FSEvents.
8. **The test's directory (4.9):** `/app`, rather than modelling `/dev`'s
   listing.
9. **Staging (7):** six PRs, 4 in three parts.
